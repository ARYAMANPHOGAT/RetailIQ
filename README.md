# RetailIQ — Intelligent Retail Demand Forecasting & Inventory Risk Prediction System

RetailIQ is a locally run Streamlit application that

* forecasts **next-day Units Sold** for every Store ID + Product ID (Linear Regression vs Random Forest),
* flags **inventory risk** with transparent, rule-based coverage analysis,
* groups store-product behaviour into **segments** with K-Means and visualises them with **PCA**,
* saves every analysis to a local **SQLite** history and exports **CSV** and **PDF** reports.

It is an undergraduate Machine Learning Lab project. It uses only classical ML: preprocessing, regression,
evaluation, hyperparameter tuning, K-Means and PCA. It does not use deep learning.

> **Data honesty:** the training data is the Kaggle *Retail Store Inventory Forecasting* dataset, which is
> **synthetic**. It is not real retailer data, and the app and reports say so.

## 1. Quick start (Windows + VS Code)

**Prerequisite:** Python **3.12 or 3.13 (64-bit)** from <https://www.python.org/downloads/>. During installation,
tick **"Add python.exe to PATH"**. You need internet access only once, to install packages.

1. Extract the ZIP and open the `RetailIQ` folder in VS Code (*File → Open Folder*).
2. Double-click **`setup.bat`**, or run it in the VS Code terminal with `.\setup.bat`.
   It creates `.venv`, installs `requirements.txt` and checks that the bundled models load. If they don't load,
   it retrains them automatically (about 1 minute).
3. Double-click **`run_retailiq.bat`**. The app opens at <http://localhost:8501>.

**Manual commands** (in the VS Code terminal, PowerShell):

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1          # if blocked: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
python -m pip install -r requirements.txt
python train.py                       # optional - trained models are already included
python -m streamlit run app.py        # launch (same as: streamlit run app.py)
```

macOS / Linux: `python3 -m venv .venv && source .venv/bin/activate`, then use the same commands.

* **Main app file:** `app.py`
* **Training command:** `python train.py` (or `train_models.bat`)
* **Tests:** `python -m pytest`

| Property | Verified value |

| Column | Type | Required |
|---|---|---|

| Store ID | text | yes |

| Price | number ≥ 0 | yes |

* `.csv` or `.xlsx`, ≤ 50 MB, ≤ 500,000 rows. Header case and extra spaces are matched automatically.
* Blocking errors, reported with the exact column and spreadsheet row numbers: missing required columns, empty values,
  invalid dates, non-numeric or negative numbers, Discount > 100, duplicate Date + Store + Product,
  and no series with 7 consecutive recent days.
* Warnings, which don't block: missing days, which are **never filled**; series that can't be forecast or
  segmented; unrecognised columns; store/product IDs not seen in training. Unseen IDs are one-hot encoded as
  "unknown", so their forecasts use only sales history and the calendar.
* A series needs its **7 most recent consecutive days** to be forecast and **28** to get a segment.
* The template (in-app download, or `data/templates/`) contains 8 valid days for one series.

## 4. How it works

```
             ┌──────────── offline: python train.py ────────────┐
raw CSV ──►  │ inspect → validate → lag/rolling features         │
             │ → chronological split (last 20% of dates = test)  │──► models/*.joblib + metadata.json
             │ → date-grouped CV + GridSearch → select by CV MAE │
             │ → K-Means/PCA on 28-day profiles → demo + template│
             └───────────────────────────────────────────────────┘
app (Demo file or Live upload) → validate → same feature code → saved model predicts (no retraining)
     → risk rules → segment assignment → SQLite save → dashboard / CSV / PDF
```

### 4.1 Target and features (next-day forecasting)

For each series and each **cutoff day t**, the model predicts **Units Sold on t+1**.

| Feature | Meaning | Known at cutoff? |
|---|---|---|
| `lag_1` | Units Sold on day t (1 day before the target) | yes |
| `lag_7` | Units Sold on day t−6 (7 days before the target) | yes |
| `roll_mean_7`, `roll_std_7` | mean / std of Units Sold over t−6 … t | yes |
| `target_dow`, `target_month` | weekday and month of the target day t+1 | yes (calendar) |
| `Store ID`, `Product ID` | stable identifiers | yes |

Categorical inputs are one-hot encoded with `OneHotEncoder(handle_unknown="ignore")`, and numeric inputs are
standardised. Both steps are stored **inside** the saved scikit-learn `Pipeline`, so training and the app always
preprocess in the same way.

### 4.2 Leakage prevention

* All lags and rolling windows are grouped by Store ID + Product ID and sorted by date. The rolling window ends
  **on** the cutoff day, so it never includes the target day. A unit test changes the target-day sales and checks
  that the features stay identical.
* Missing days stay empty (NaN). Any window that touches a gap is dropped, so no history is invented.
* **Excluded inputs:** `Demand Forecast` (0.997 correlation, which would give R² ≈ 0.99 for the wrong reason).
  Also excluded: price, discount, promotion, weather, competitor price, units ordered and inventory **for the
  target day**, because they are not known in advance. Current inventory is used only for risk analysis.

### 4.3 Chronological validation and tuning

* **Holdout test:** the final 20% of unique target dates, **2023-08-10 → 2024-01-01** (14,500 rows).
  Training covers 2022-01-08 → 2023-08-09 (57,900 rows). Every row of a given date sits in the same split, and the
  two splits never overlap.
* **Tuning:** `GridSearchCV` with 3 **date-grouped expanding-window folds** (TimeSeriesSplit applied to unique
  dates), inside the training period only. The RF grid is `max_depth ∈ {8, 16}`, `min_samples_leaf ∈ {20, 100}`,
  `n_estimators = 100` and `max_features = 0.33`. The best result was depth 8 with leaf 100.
* **Selection rule:** lowest mean **validation** MAE. The test set is never used to choose a model.
  CV MAE was LR 89.36 vs RF 89.30, so **Random Forest** was selected.
* Negative predictions are clipped to 0 (demand can't be negative).
* The deployed model is the one trained on the training period. That way the holdout scores describe exactly the
  model the app uses, and the demo data (which comes from the holdout period) is genuinely out-of-sample.

### 4.4 Results (holdout test, real numbers from `models/model_metadata.json`)

| Model | MAE | RMSE | R² |
|---|---|---|---|
| Linear Regression | 88.75 | 108.20 | −0.0005 |
| **Random Forest (selected)** | 88.78 | 108.21 | −0.0008 |
| Naive: yesterday's sales | 119.75 | 153.49 | −1.014 |
| Naive: 7-day rolling mean | 93.19 | 115.45 | −0.139 |

**Interpretation (important for the viva):** in this synthetic file, next-day sales are statistically unrelated
to past sales. Their correlation with lag 1, lag 7 and the rolling means is ≈ 0.00. No honest next-day model can
explain much variance, so R² ≈ 0 and both models learn each series' typical level (≈ 136 units). They still beat
the naive rules on MAE by 4.4 to 31 units. A high R² here would be a sign of leakage, not skill.

* **MAE:** average absolute miss in units. **RMSE:** like MAE, but penalises large misses more.
  **R²:** share of variance explained (0 = as good as predicting the mean; < 0 = worse than the mean).

### 4.5 Feature importance

* **Permutation importance** of the *selected* model on the holdout set: how much MAE increases when one input
  column is shuffled. All values are ≈ 0, which is consistent with there being no signal.
* **Random Forest impurity importance**, grouped back to the original inputs. It is computed on training data and
  favours continuous features even when they carry no signal, so read it alongside the permutation chart.
* Importance shows **association, not causation**.

### 4.6 Inventory risk (rule-based, not a trained model)

```
recent_avg_demand = mean Units Sold over the last 7 calendar days of the series
coverage_days     = current inventory (latest day) / recent_avg_demand
High   : coverage < 1 day      Medium : 1 ≤ coverage < 3 days      Low : ≥ 3 days
recent_avg_demand < 0.5/day  → coverage not computed (no division by ~0) → Low, "No meaningful recent demand"
estimated replenishment = max(0, ceil(3 × recent_avg_demand − inventory))   ← an ESTIMATE, not a purchase order
```

All thresholds are in `config.py` (`RISK_*`, `MIN_DEMAND_PER_DAY`, `TARGET_COVER_DAYS`). Because the dataset has
no stockout label, RetailIQ does not claim a stockout probability.

### 4.7 Product segmentation (K-Means + PCA)

* **Profiles:** each series is cut into complete, non-overlapping **28-day windows**, giving 2,600 training
  profiles. Each profile has 6 features: average units sold, demand std, average inventory, sell-through
  (sold ÷ inventory), average price and average discount. All windows are the same length, so profiles from
  training and from uploaded files are comparable.
* **Scaling:** `StandardScaler`. **K-Means** is evaluated for k = 2…8 with the elbow method (inertia) and the
  silhouette score. k is the best silhouette **within 3–6** (k = 2 is too coarse to be useful). Result:
  **k = 5, silhouette 0.158**, which means weak separation. That is expected with synthetic data and is
  reported honestly.
* Segment names such as "Higher sales, Higher sell-through" are generated from each centroid's two most distinctive
  standardised features. They describe measured averages and are not ground truth.
* **PCA** (2 components, 59.6% of the scaled variance) is used **only for the 2-D plot**.
* In an analysis, each series is assigned to a segment using its **latest 28 consecutive days**. The scaler, K-Means
  and PCA are saved together in `segmentation_bundle.joblib`.

### SQLite history, exports and privacy

`database/retailiq.db` has three tables:

* `analysis_runs`: id, timestamp, mode, source file, record count, forecast date, model version, status, and a JSON
  summary with daily totals.
* `prediction_results`: next-day forecasts (`actual_units` is NULL) and backtest predictions with real actuals.
* `product_insights`: inventory, recent demand, coverage, risk, replenishment estimate, segment and PCA coordinates.

Each analysis is saved in one transaction, so a failed save stores nothing. Queries are parameterised, and child
rows cascade on delete. **Uploaded files are processed in memory and never stored.** The PDF report contains
metadata, a dataset summary, model and forecast details, risk and segmentation summaries, and limitations, all as
real tables with no decorative charts.

## 8. Viva guide

**Q: What problem does RetailIQ solve?** It estimates tomorrow's demand per store-product, shows which items may
run short soon, and groups items with similar behaviour, which supports replenishment decisions.

**Linear Regression.** Fits `y = w·x + b` by least squares. Input: the 8 features after one-hot encoding and
scaling. Output: predicted units. Why: a simple, explainable baseline. Fitting costs about O(n·p²) for n rows and
p columns.

**Random Forest Regressor.** Builds 100 decision trees, each on a bootstrap sample with random feature subsets, and
averages their predictions. It captures non-linear effects and interactions. Training costs about
O(T · n log n · m) for T trees and m features tried per split, and prediction about O(T · depth). Its parameters
were tuned with GridSearchCV on time-ordered folds.

**Why not shuffled K-fold?** Random splits let the model train on days after the ones it is tested on, which
leaks the future. We split by date and validate on later dates only.

**Metrics.** MAE (average miss), RMSE (penalises big misses), R² (variance explained). We also compare against
naive baselines, which is how we know the model adds value despite R² ≈ 0.

**Why is R² ≈ 0?** The synthetic data has no day-to-day sales pattern; we measured lag correlations of ≈ 0. Getting
R² ≈ 0.99 would require the leaky Demand Forecast column. Reporting this honestly is a key learning outcome.

**K-Means.** Repeatedly assigns points to the nearest centroid and moves each centroid to the mean of its points.
Cost per iteration is about O(n·k·d). The elbow method (inertia vs k) and the silhouette score (cohesion vs
separation, from −1 to 1) guide the choice of k.

**PCA.** Finds orthogonal directions of maximum variance (eigenvectors of the covariance matrix) and projects the
6-D profiles to 2-D for plotting. Cost is about O(n·d² + d³). It is used for visualisation only.

**Inventory risk.** A transparent rule (days of cover) rather than a classifier, because the data has no stockout
labels. A supervised model needs a ground-truth target.

**Leakage checks.** The features use only data up to the cutoff day, a unit test proves it, Demand Forecast is
excluded, and future-day prices and promotions are excluded.

**Limitations.** The data is synthetic; forecasts sit close to typical levels; risk uses fixed thresholds and
ignores lead times; segments are weakly separated; the app forecasts only one day ahead; uploads must follow the
documented schema.

**Possible extensions.** Real sales data, multi-day horizons, supplier lead times in the risk rule, and
promotion/price plans supplied by the user as known future inputs.
